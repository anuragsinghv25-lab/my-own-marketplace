# R1.1 · Standard taxonomies (Shopify-style tree, Shopify and UNSPSC adoption)

**Goal:** stop typing every level of the category tree. Category managers start from proven standards (the Shopify Standard Product Taxonomy and UNSPSC) and adopt only what the marketplace needs, with each adopted category arriving with the attributes that describe its products. Custom categories stay possible everywhere.

**Depends on:** R1. **Indicative size:** 1 sprint. **Status:** built. **Decision record:** [ADR 0009](../adr/0009-standard-taxonomies.md).

## Why now (before R2)

R1 shipped a fixed five-level tree (segment › family › class › commodity › listing category) where every level was typed by hand. Building a realistic tree that way takes weeks and still misses the attributes R2 needs. Modern marketplaces (Shopify, Amazon, eBay, Google Merchant) all work from a standard taxonomy with variable depth and a set of attributes per category. Doing this before R2 means the configuration studio can start each spec sheet from a ready attribute set instead of a blank page, and R5 can use the same attributes as variant options.

## What changed from R1

| R1 | R1.1 |
| --- | --- |
| Exactly five levels, each named (segment, family, class, commodity, L5) | Variable depth up to **8 levels**, shown as a breadcrumb. Each node is a **group** (holds categories) or a **listing category** (sellers list products here; always a leaf) |
| Every node typed by hand | Nodes are **custom** or **adopted** from Shopify or UNSPSC; adopted nodes keep their standard id |
| UNSPSC-looking numeric codes for custom nodes (`10101510-01`) that could clash with real UNSPSC codes | Custom codes `C01`, `C01.03`, `C01.03.12`; adopted nodes use the standard's id (`el-6-11-2`, `43211503`). Existing codes were migrated (`10101510-01` → `C10.10.15.10.01`) |
| No attributes on categories | Each category has an **attribute set**, inherited down the tree; R2 starts the spec sheet from it |
| UNSPSC only as a code style | Any category can be **mapped to a UNSPSC code** for procurement reporting; children inherit it |

## Scope

| ID | Feature | Details |
| --- | --- | --- |
| F1.1.1 | Variable-depth tree | Up to 8 levels; group vs listing category; listing categories cannot have children; a childless group can become a listing category (needs an alias, creates draft v0) and a listing category still in draft can become a group again. Moving re-computes levels for the whole subtree |
| F1.1.2 | Standard taxonomies page | Admin › Standard taxonomies. **Shopify** release bundled with Orbita (MIT licence), loaded one vertical per request with a progress bar; resumable; a newer bundled release shows "Update". **UNSPSC** uploaded by the admin (Excel or CSV from the official source; not shipped, licence is the customer's), parsed in the browser, sent in chunks of 2,000 |
| F1.1.3 | Add from standard | From the tree (top level or inside any group): Shopify / UNSPSC tabs, search (names, UNSPSC code prefixes) or browse level by level; detail panel with path, level, subcategory count and the attributes with their value counts; marks what is already in the tree |
| F1.1.4 | Adopt | Add as listing category or group. Placement: follow the standard's path (missing parents are adopted as groups) or put it under one of your groups. Optionally bring a whole branch (up to 150 nodes): groups stay groups, leaves become listing categories with automatic unique aliases |
| F1.1.5 | Attributes from Shopify | Adopting a Shopify category imports its attributes into the library as multi-select attributes with value lists (extended attributes such as "Lens color" share their base list). An attribute already in the library with the same name or code is reused, never duplicated. Attached to the category as its attribute set, skipping attributes it already inherits |
| F1.1.6 | Category attribute set | Node panel shows own and inherited attributes ("from Electronics"), origin (Shopify / manual), required toggle, add from library, remove |
| F1.1.7 | UNSPSC mapping | 8-digit code per category (validated against the loaded codeset when present); adopted UNSPSC nodes map themselves; inherited by children |
| F1.1.8 | Provenance everywhere | Tree shows an S / U marker; node badges show source and standard id; library shows "from Shopify"; the tree API returns `kind`, `source`, `externalId`, `unspscCode` |

## Data added

`reference_taxonomies` (one row per standard: release, counts, loaded parts), `reference_categories` (source, standard id, parent, level, name, full path, attribute handles, leaf), `reference_attributes` (handle, name, description, base handle, values), `category_attributes` (node, attribute, required, order, origin). New columns: `category_nodes.kind`, `source`, `external_id`, `unspsc_code`; `attributes.source`, `external_ref`; `value_lists.source`, `external_ref`. New permission subject `StandardTaxonomy` (platform admin loads; category managers, approvers and auditors read).

## Out of scope

Applying a newer Shopify release to adopted categories (diff and apply: R6). Variant options from the attribute set (R5). Mapping to Google product taxonomy for feeds (R9). Search and filters for buyers (marketplace, later).

## Exit demo

1. The platform admin loads Shopify 2026-10 (26 verticals, 14,606 categories) and uploads a UNSPSC file.
2. The category manager searches "gaming laptops", adopts it as a listing category; Electronics › Computers › Gaming Computers are created as groups and 17 attributes (Color, Processor family, Operating system…) arrive in the library and on the category.
3. From Electronics, they browse to Networking › Modems and adopt the whole branch: 1 group plus 3 listing categories, each with an alias and draft v0.
4. They adopt UNSPSC 43211602 "Docking stations" (segment, family and class created) and map Gaming Laptops to UNSPSC 43211503.
5. They create a custom group "Office & stationery" with Color, add listing category "Pens" under it, and see Color inherited.

## As built

| Item | Decision |
| --- | --- |
| Shopify data | Compact per-vertical bundle generated by `packages/modules/standards/scripts/build-shopify.mjs` from the v2026-10 release (5 MB raw, about 1 MB in git). Loading all 26 verticals takes a few seconds; each request handles one vertical, safe for serverless limits |
| UNSPSC data | Never committed to the repository. The parser accepts any layout where an 8-digit code sits next to its title (flat Segment / Family / Class / Commodity exports and one-code-per-row files) |
| Reload | Re-loading or updating replaces only the reference rows; adopted categories and imported attributes are untouched |
| Attribute type | Shopify attributes become `multi_enumerable` (several from a list); attributes without values become text. R2 can narrow a category's use of them |
| Aliases | Single adoption asks for aliases (name pre-filled for leaves). Branch adoption uses the name, then "Name (Parent)", then "Name · id" |
| Permissions | Adoption follows the same rules as creating: a workgroup category manager adopts only inside their subtree and cannot create top-level groups (the dialog offers their groups instead) |
| Audit | `standards.load_started`, `standards.loaded`, `taxonomy.node.adopted`, `library.attributes.imported`, `taxonomy.node.kind_changed`, `taxonomy.node.unspsc_mapped`, `taxonomy.attribute.added/updated/removed` |
| Tests | 11 integration tests (loading, search, adoption, branch, attribute inheritance, kinds, levels on move, UNSPSC import and mapping, code migration) plus bundle integrity tests; browser run of the exit demo |
